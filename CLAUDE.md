# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

The artifact appendix for the paper *A Unified Feature Model for Microservice
Identification and Refactoring* (Almeida & Rito Silva, 2026). It is not an
application: it is a research data package plus a GitHub Pages site that
presents it. There are no tests and no lint config.

## Commands

```sh
python3 generate.py            # regenerate pages/ from artifacts/ (stdlib only, run from repo root)
bundle install                 # install the pinned Jekyll (vendor/bundle, see .bundle/config)
bundle exec jekyll serve        # local preview at http://localhost:4000/UnifiedFeatureModelArtifacts/
```

Browse the preview at that full URL, baseurl included. The bare root
(`http://localhost:4000/`) 404s, and because asset URLs are absolute the result
looks like a page whose stylesheet silently failed to load.

`generate.py` prints a per-tool colour-count table that must match the paper's
mapping-summary table, and exits non-zero (`BuildError`) if any expected
analysis, profile, or image is missing. It has no flags and no partial mode —
it always rebuilds everything.

## The one build invariant

GitHub Pages builds the committed tree and **never runs `generate.py`**.
Therefore `pages/` is committed on purpose (see the note in `.gitignore`), and
**any change under `artifacts/` requires re-running `generate.py` and committing
the regenerated `pages/`**, or the published site silently goes stale.

Corollary: never hand-edit a file in `pages/` that carries the
`<!-- GENERATED by generate.py -->` banner — `prune_pages()` deletes every
bannered file at the start of each run. `pages/index.md` is the only
hand-written page (it has no banner, so it survives).

## Architecture

**`artifacts/` is the single source of truth and is published in place.** The
Pages source is the repository root, so `artifacts/` sits inside the Jekyll
source tree. Nothing is ever copied out of it; the `Artifacts` class in
`_pages_gen/artifacts.py` only maps logical keys
(`images/CARGO_claudeMapping.png`, `profiles/MEM.profile`) to real paths and
turns them into URLs. Generated pages link and embed the artifact files — they
never inline their content, which is why the pages stay short and the artifacts
stay canonical.

Data flow: `artifacts/` → `generate.py` → `pages/*.md` (Markdown + inline HTML
with YAML frontmatter) → Jekyll (`_layouts/default.html`, `_config.yml`) →
`_site/` (gitignored locally; GitHub builds its own).

### The `_pages_gen/` package

`generate.py` is a ~30-line entry point; the build lives in `_pages_gen/`
beside it. **The leading underscore is load-bearing**: Jekyll skips entries
whose name starts with `_` *before* it consults `exclude:`, so without it the
generator source would be published as site content. (`- _pages_gen` is also
listed under `exclude:` as a second layer.)

Stdlib only, layered bottom-up — each module imports only from the ones above
it in this list, so the graph stays acyclic:

| Module | What it holds |
| --- | --- |
| `paths.py` | `REPO` / `ARTIFACTS` / `PAGES`, and `BuildError` |
| `config.py` | every table that varies; no logic |
| `util.py` | `read`, `human_size`, `png_size` |
| `artifacts.py` | the key→file registry, and the one built artifact (the zip) |
| `parse.py` | `.profile`, FeatureIDE XML, `SKILL.md`, paper inventories |
| `render.py` | HTML/Markdown fragments, `sub_nav`, `write_page` |
| `pages/` | one module per site section: `model`, `meta_review`, `skills`, `evaluation` |
| `report.py` | the colour-count cross-check |
| `postprocess.py` | `prune_pages`, `apply_baseurl` |
| `cli.py` | `build()` and `main()` |

The five Evaluation renderers share `pages/evaluation.py` deliberately: they
share the `sub_nav` strip, the tool→paper lookup, and the "Proposed model
extension" block.

`render.py` receives an `Artifacts` instance as a parameter and only reads it;
`artifacts.py` never imports `render.py`.

Almost everything that varies lives in `_pages_gen/config.py`, so adding or
renaming a tool is a config edit, not a code edit:

- `TOOLS` / `TOOL_LABEL` — the seven mapped tools, in the paper's order
- `TOOL_META` — per tool: which skill produced its mapping, its source paper, its repo URL
- `IMAGE_PREFIX` — `exportedImages/` uses different casing from `analyses/` for some tools
- `PAPERS` — the three source papers; tool membership is derived from `TOOL_META["source"]`, never duplicated
- `MERGED` — the union profiles (`all-tools`, `wang`, `mono2micro+Micro2Micro`)
- `COLOURS` / `COLOUR_MEANING` / `COLOUR_SHORT` — the mapping colour semantics from the paper
- `SKILL_ORDER` / `SKILL_SUMMARY` — the six skills in pipeline order, with reader-facing prose

Two things to know about page generation:

- Pages emit a `{{BASE}}` placeholder for URLs; `apply_baseurl()` rewrites it to
  `{{ '/x' | relative_url }}` as the last step. Writing Liquid directly would
  collide with escaping. The regex matches non-whitespace, so URLs containing
  spaces must be percent-encoded before that point (`Artifacts.url` does this —
  it matters for the meta-review CSV/PDF filenames).
- Evaluation navigation is static HTML (`sub_nav()`) rather than client-side
  tabs, deliberately: an artifact appendix gets cited by URL, so every tool page
  must be deep-linkable.

### artifacts/ layout

```
feature_model/          The canonical model: feature_model.xml (FeatureIDE) + extended.png,
                        and .profiles/<tool>.profile — the per-tool colour mappings.
initialFeatureModelFromMono2Micro/
                        The pre-generalisation model, kept for comparison.
evaluation/
  analyses/<tool>/      analysis.md (every finding cites file:line or a doc link) + README.md
  feature_models/<tool>/  Extended models: the tool's features added to a copy of the model
  exportedImages/       <tool>_claudeMapping.png (skill output), _revisedMapping.png
                        (authors' correction), _extendedMapping.png, _manualMapping.png
  papers/               Per-paper tool inventories — excluded from the site (third-party
                        PDF links); generate.py lifts the venue/availability columns instead
meta-review/            The meta-review CSV + PDF (filenames contain spaces)
.claude/skills/         The six mapping skills that produced the evaluation
```

Naming conventions the generator depends on: an automated profile is
`<stem>.profile` and its reviewed twin is `<stem>_user_review.profile` — with
one exception, `mono2micro+Micro2Micro`, whose twin is
`mono2micro_user_review+Micro2Micro_user_review.profile`, special-cased in
`profile_downloads()` and `tally_profiles()`. `all-tools` also names its
extended image `all_tools_extended.png` while every other family uses
`_extendedMapping.png` (normalised in `render_union_page`).

A `.profile` is a flat `feature=Colour` list; line 1 is the default-profile
flag and the trailing `featureColorMeaning*` lines are the legend, not features
(see `parse_profile`).

### The skills

`artifacts/.claude/skills/` holds the six Claude Code skills that produced the
evaluation: `extract-codebases-from-paper` → `codebase-map` / `docs-map` →
`verify-analysis` → `merge-profiles`, plus the orthogonal
`refresh-feature-model-infos`. These are **published research artifacts, not
tooling for this repository** — they were run against a different working
layout (paths inside them like `feature_model/representation/.profiles/` do not
match this repo). Treat them as archived source: they are what the paper's
reproducibility claims point at.

The mappings are LLM-produced and non-deterministic, which is why every mapping
ships in both automated and reviewed form, and why `verify-analysis` exists.

## Jekyll configuration traps

`_config.yml` carries long comments explaining these; the short version:

- `include:` entries must be **bare basenames**. A path-qualified entry such as
  `artifacts/feature_model/.profiles` matches nothing and fails *silently* —
  a clean build with every `.profile` missing. `.profiles` and `.claude` are
  listed there; without them the dot-prefix rule drops them.
- Both `include:` and `exclude:` **replace** Jekyll's defaults rather than
  extend them, hence `.htaccess`, `vendor`, `Gemfile` etc. being repeated.
- `SKILL.md` has YAML frontmatter, so Jekyll renders it to `SKILL.html` and no
  raw `.md` is emitted. Download links for skills must point at
  `raw.githubusercontent.com` (`RAW_BASE` in `generate.py`); a link to
  `artifacts/.claude/.../SKILL.md` would 404. The `references/*.md` files have
  no frontmatter and are copied verbatim.
- The `Gemfile` pins `github-pages`, not bare `jekyll`, so local preview matches
  GitHub's Jekyll 3.9.x. The extra stdlib gems (`webrick`, `csv`, `base64`,
  `bigdecimal`, `erb`) are needed to boot on Ruby 3.4.
- `baseurl: /UnifiedFeatureModelArtifacts` must match the repository name or
  every absolute asset path 404s.

## Prose conventions

The site and README use British spelling (*colour*, *generalisation*,
*licence* in prose) and en/em dashes. Generated page text lives inside
`generate.py` as Python string literals — user-facing wording changes are edits
to that script, not to `pages/`.
